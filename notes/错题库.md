## 知识梳理

### 一、核心概念

**Agent vs Chatbot 本质区别**
- Chatbot：被动回复，你说一句它回一句，只动嘴
- Agent：**自主闭环执行**，规划 → 调工具 → 看结果 → 再规划，能动手
- 核心：**Chatbot 动嘴，Agent 动手+动脑闭环**

**Agent 标准 7 大模块**
- 感知 → 推理 → 规划 → 记忆 → 工具 → 行动 → 反思
- 面试官要的是**分层架构**，不是"用了什么组件"

### 二、核心技术

**ReAct 循环**
- Thought → Action → Observation，循环直到给出答案

**记忆三层**
- 工作记忆（当轮推理临时变量）、短期记忆（会话上下文）、长期记忆（跨会话持久化）

**混合检索**
- 关键词搜索（BM25）：精确匹配编号/术语，但搜不到同义词
- 向量搜索：语义匹配不同表述，但精确匹配差
- 两者**互补**，双路召回 → Rerank → Top N

**MCP 协议**
- 专为 LLM 设计的标准化工具协议，核心优势：**标准化 + 自动发现**
- 和 HTTP 的区别：统一 JSON-RPC、自动发现工具、上下文感知、结构化错误

**Skills vs MCP**
- MCP = 底层协议（怎么连接工具，像 USB 接口）
- Skills = 高层功能单元（怎么完成任务，含多个工具组合 + 推理步骤）

**LangGraph**
- 有向图状态框架：节点=动作，边=条件分支
- 和手写 ReAct 原理一样，但可为不同路径单独控制逻辑

### 三、工程实践

**死循环检测**
- 模式检测比硬上限更重要：Action 历史哈希值，连续 3 次相似 > 0.95 判定循环
- 死循环**不一定报错**，工具可能都调用成功了但 agent 在重复同样的事

**成本控制（五层防御）**
- 硬限制 → Token 预算 → 美元预算 → 重复检测 → 工具熔断
- 加 cost-per-task P95 告警

**生产环境排查（四步）**
- 先怀疑数据（分布漂移）→ 再怀疑工具（mock vs 真实）→ 再看模型版本 → 最后看长尾输入

**工具 Schema 设计**
- 描述性参数名 + 参数描述加示例值 + Enum 限制 + Schema 精简 + 严格类型

**工具幻觉排查**
- ①工具是否传入 API ②Prompt 是否提了未接入的工具 ③Schema 是否有歧义

**千轮对话上下文管理**
- 短期记忆（滑动窗口）+ 长期记忆（摘要压缩 + 向量库）+ 召回机制

**Agent 评估五维度**
- 任务完成率 / 工具调用准确率 / 效率（轮数+Token）/ 鲁棒性 / 输出质量

**大规模工具管理**
- 不让模型同时看到所有工具 → 分类/动态加载/向量检索/分层 Agent

**Agent 安全**
- ⭐ **提示注入**（Agent 特有风险，用户输入藏恶意指令）
- 工具权限过大 / 敏感信息泄露 / 资源耗尽
- 防范：输入输出隔离、敏感操作二次确认、工具分级

**2026 趋势**
- 从框架到协议 / 评估驱动开发 / 可观测性 / 成本工程 / 多 Agent 分工

## 2026-07-15

**Q: AI Agent 和普通 Chatbot/LLM 的本质区别是什么？**
- 我的回答：前者是一个具有设计，问答，规划集一身的东西，后者只是前者的大脑负责思考
- 正确回答：Chatbot 只能被动回复（你说一句它回一句），Agent 能**自主闭环执行**——你给一个目标，它自己反复规划 → 调用工具 → 观察结果 → 再规划直到完成。Chatbot 只动嘴生成文字，Agent 能动手（调工具、写文件、搜索等）并根据结果自主推进。Chatbot 也能多轮对话（通过传历史），但它不能自主执行动作。
- 关键遗漏：没提到"自主闭环执行"和"工具调用反馈循环"

**Q: Agent 标准架构通常包含哪些核心模块？**
- 我的回答：调用大模型，外部工具，MCP工具，记忆系统，错误处理，文档搜索
- 正确回答：标准 Agent 架构包含 **7 个模块**：①感知（输入解析） ②推理（ReAct/CoT 决策引擎） ③规划（目标分解、任务排序） ④记忆（工作/短期/长期） ⑤工具（外部能力封装） ⑥行动（执行动作） ⑦反思（自评估纠错）
- 问题分析：只说了"用了什么组件"，没说"系统怎么分层设计"——面试官要看的是架构思维

**Q: Agent 的记忆通常分哪几个层次？各有什么作用？**
- 我的回答：不知道
- 正确回答：三层记忆——**工作记忆**（当前推理步骤的临时变量，不跨调用）、**短期记忆**（会话上下文，滑动窗口 + 缓存）、**长期记忆**（跨会话持久化，向量数据库或结构化存储）

**Q: 为什么要用混合检索（关键词 + 向量）？**
- 我的回答：关键词更精准，向量搜索范围大但不准确
- 正确回答：两者是互补关系。**关键词搜索**擅长精确匹配（专有名词、编号、代码），但搜不到同义词/近义表达。**向量搜索**擅长语义匹配（不同表述相同意图），但对精确匹配效果差。混合检索 = 双路召回 → 去重 → Rerank → Top N
- 问题分析：把关键词说成"更精准"不准确——它在精确匹配上强，但语义覆盖弱。两者是不同维度的互补，不是优劣关系

**Q: MCP 是什么？和普通 HTTP 工具调用有什么区别？**
- 我的回答：模型上下文协议，像外部插件，区别说不清楚
- 正确回答：MCP = Model Context Protocol，专为 LLM Agent 设计的标准化工具接入协议。和普通 HTTP 的区别：①**标准化**（统一 JSON-RPC 格式，不用各写各的文档） ②**自动发现**（MCP Client 启动时自动拉取工具列表，不用手动对接） ③**上下文感知**（工具结果直接注入对话） ④**结构化错误**（让 LLM 能理解并恢复，而不是只返回 HTTP 状态码）
- 关键遗漏：没说清楚"自动发现机制"和"标准化"这两个核心优势

**Q: Agent 进入死循环怎么办？有哪些检测和解决方案？**
- 我的回答：减少循环次数、try-except 错误处理、Prompt 告诉模型持续报错就停止
- 正确回答：检测方法——①**硬上限**（max_turns） ②**模式检测**（记录 Action 历史哈希值，连续 3 次相似度 > 0.95 判定循环）。解决方案——①强制跳出 ②加随机扰动改变决策路径 ③Prompt 约束 ④结构化规划
- 问题分析：把"错误处理"和"死循环检测"混为一谈了——死循环不一定报错，可能工具都调用成功了但 agent 在重复同样的动作。模式检测才是面试官最想听到的关键

**Q: 如何控制 Agent 的成本（Token 消耗和 API 调用费用）？**
- 我的回答：减少 HTTP 工具增加 MCP 工具、减少循环次数、action 相似度检测终止、Prompt 约束
- 正确回答：五层防御——①**硬限制**（max_turns + max_tokens） ②**Token 预算**（每次 API 调用的 max_tokens + 总 Token 预算/任务） ③**美元预算**（每任务费用上限，超了熔断） ④**重复检测**（Action 历史相似度终止） ⑤**工具熔断**（连续失败 N 次后禁用）。再加 cost-per-task 的 P95 告警监控
- 问题分析：说"减少 HTTP 工具增加 MCP 工具"不对——MCP 不省成本，核心是预算控制和熔断机制没说

**Q: 什么时候应该用多 Agent 架构？什么情况下单 Agent 就够了？**
- 我的回答：不知道，没学过
- 正确回答：单 Agent 能搞定就**绝不上多 Agent**。多 Agent 场景：①任务可清晰分解 ②不同 Agent 需不同工具权限 ③需要并行处理独立子问题。单 Agent 够用就别上多 Agent——复杂度指数级上升
- 关键：默认单 Agent，只在有明确拆分理由时才上多 Agent

**Q: Agent 从开发到上线，如果生产环境表现比测试差，怎么排查？**

## 2026-08-05（模拟面试回测）

> 回测结果：记忆三层 ✅ 已掌握；Agent vs Chatbot ✅ 基本掌握（差"闭环"二字）；ReAct 循环、工具幻觉、评估五维度仍需巩固，见下。

**Q: ReAct 循环的定义？（上次把"感知思考行动反思"当成了 ReAct）**
- 正确回答：ReAct 循环 = **Thought → Action → Observation** 三步闭环，循环直到模型直接回答。**"感知→思考→行动→反思"是 Agent 架构的 7 大模块，不是 ReAct 循环**，两个层面别混。

**Q: 流式 tool_calls 为什么按 index 累加 arguments？**
- 正确回答：流式把一次工具调用的 `arguments` 切成多片**分片到达**，用 `=` 赋值只留最后一片、JSON 残缺，`json.loads` 必失败；必须 `+=` 拼回完整 JSON。按 index 分桶是因为**一轮可能同时发多个工具调用**。
- 口诀：name 可能一次到，arguments 必分片；index 分桶、arguments 累加、最后 json.loads 再 dispatch。

**Q: 模型什么时候调工具？**
- 正确回答：依据是"**当前问题需不需要工具**"，不是"工具可不可用"——工具永远在请求里（get_all_schemas 每轮都传）。模型可能该调不调、乱调（这就是工具幻觉）。

**Q: Attention 里 V 的职责？**
- 正确回答：V 是每个词携带的**内容**，输出 = 所有 V 按注意力权重做**软加权平均（凸组合）**，不是"挑最相关的一个"。

**Q: 4-bit 量化精度损失从哪来？**
- 正确回答：损失发生在**量化取整**（float32→16 档位舍入），不是反量化（反量化只是确定性映射）。省 **8 倍**显存（4字节→0.5字节）。损失小因：权重分布集中 + 大量独立误差互相抵消。

**Q: 死循环检测？**
- 正确回答：两层——① **max_turns 硬上限**（agent_core.py 里就有！）② **Action 历史相似度模式检测**（连续 3 次 > 0.95 判定）。死循环不一定报错。解决：强制跳出 / 随机扰动 / prompt 约束 / 结构化规划。**排查先怀疑模型决策，再查工具。**

**Q: 工具幻觉排查（再次答错：又答了预防措施）**
- 问题分析：**排查 ≠ 预防**！面试官要的是"已报错怎么定位"，不是"怎么防未来"。
- 正确回答顺序：① 工具是否真传入 API（请求里有没有 tool schemas）② Prompt 是否提了未接入的工具名 ③ Schema 是否有歧义。

**Q: Agent 评估五维度**
- 正确回答：① **任务完成率**（最重要）② **工具调用准确率** ③ 效率（轮数+Token）④ **鲁棒性**（异常恢复）⑤ 输出质量（幻觉率/相关性）。幻觉率只是 ⑤ 的子项，不是独立维度。

**Q: 提示注入为什么 Agent 特有？**
- 正确回答：Chatbot 输入再恶意也只是"对话内容"，只生成文字；Agent 会把用户输入**当指令驱动工具执行真实动作**（删文件、发请求），"能动手"放大了危害。

**Q: 多用户改造五项（回测）
- 正确回答：① 每用户独立 messages ② user_id 路由 ③ 并发安全（加锁/无共享）④ 记忆分库（按用户分文件）⑤ 模型路由。当前项目 memory.json 全局单份是最大单用户假设。

**Q: CS 基础（MCP 原理）——stdin/stdout、HTTP、子进程**
- stdin/stdout = 程序默认的两条管道（输入/输出），可重定向。MCP 用它传 JSON-RPC：Client 写 Server 的 stdin、读 stdout（mcp_client.py / mcp_server.py 就是）。
- HTTP = 跨机器的客户端-服务器协议（请求/响应）。本地工具用 stdio，远程服务用 HTTP。
- 子进程 = subprocess.Popen 自动启动另一个程序，相当于代码里替人敲命令行。

**Q: 一次 HTTP 调用的完整顺序？（答错过：把"找 IP"放到了"发请求"之后）**
- 正确顺序五步：① DNS 翻译域名找 IP → ② TCP 三次握手建立连接 → ③ 发 HTTP 请求（方法+headers+body）→ ④ 服务器回状态码（200/401/500）→ ⑤ 流式响应（SSE 逐片 data 块）。
- 口诀：先认路 → 再握手 → 再发信 → 等回执 → 收货。**找 IP 和建连接必须发生在发请求之前。**
- 状态码：2xx 成功 / 4xx 客户端错（404、401、429）/ 5xx 服务器错。

**Q: 进程基础**
- 进程 = 运行中的程序，内存独立（隔离，崩了不连累别人），有 PID，退出码 0=正常。
- 子进程 = subprocess.Popen 自动启动另一个程序（相当于代码里替人敲命令行）。
- 进程间通信（IPC）：管道（MCP 的 stdin/stdout）、文件（memory.json）、socket。
- 进程 vs 线程：进程内存各自独立；线程共享内存（并发安全要加锁）。多用户并发改共享数据 = 并发安全问题。

**Q: localhost / 端口 / 部署**
- localhost(127.0.0.1) = 本机回环地址，访问自己。端口 = 一台机器上区分不同服务的房间号。
- Flask 部署：Flask 是服务器本身，监听端口；curl/浏览器是客户端。请求 → localhost:5000 → OS 根据端口找到 Flask 进程 → Flask 调模型 → 返回响应。
- 生产网络问题：超时（设超时）、重试（指数退避）、限流 429（降频）。排查：ping 测通、curl 手动请求、看状态码分 4xx/5xx。

**Q: 幻觉根源 + temperature 误区（新学）**
- 根源三层：① LLM 是"下一个词预测器"，学的是"听起来合理"不是"事实" ② 模型**被迫输出**（没有"我不知道"的默认选项），不知道就编造 ③ 知识是**有损压缩**进参数，精确事实（数字/日期）最易失真。
- 误区：temperature 高会增加发散，但**幻觉在 temperature=0 时照样发生**——temperature 只影响发散度，不影响编造。
- RAG 缓解：用外部知识做依据，**降低**幻觉率而非**消除**。

**Q: temperature / top_p 采样参数（新学）**
- temperature：越高概率分布越平（各词差距缩小）、越低高概率词更突出。控制"发散/大胆程度"。
- top_p：核心采样（nucleus），累计概率达到 p 的最小词集，越大候选词越多。
- 要稳定保守：temp 0.2~0.5 + top_p < 0.9；要创造性：temp 调高。Agent 调工具建议低 temperature。

**Q: 上下文窗口瓶颈 / KV Cache（新学）**
- 主瓶颈：**KV Cache 显存线性增长**——每个 token 存一份 K,V，7B 模型每 token 几 KB，128K 上下文占几个 GB。
- 次瓶颈：注意力二次复杂度。KV Cache 把生成从 O(n³) 优化到 O(n²)。
- 缓解：Flash Attention、滑动窗口/稀疏注意力、KV Cache 压缩淘汰。

- 通用原则："为什么不用更重的方案"这类题，从"规模 / 需求 / 成本"三个维度答。
